# 浏览器性能测量

性能判断以核心实际帧率和仿真速度为准。页面的 `requestAnimationFrame` 频率只反映网页回调，不能代表游戏速度；30 FPS 的游戏在仿真速度接近 100% 时可以正常运行。静止画面不一定持续提交新帧，因此也不能只看实际 FPS。

短窗口读数会随采样相位波动，停止时还可能包含不足一秒的尾段。比较完整的 60 秒记录和多轮结果，不用最后一个样本判断整体速度。

## 在手机上采样

先确认浏览器提供 WebGL2、WebAssembly SIMD、跨源隔离和 SharedArrayBuffer。网页会在初始化音频和加载核心前检查这四项能力，缺失时列出原因；隔离修复等待最多 10 秒，失败后返回诊断。部分应用内 WebView 即使收到正确的 COOP/COEP 响应头，也没有开放共享内存，此时应在完整浏览器中重新检查。未通过能力检查时，不生成游戏性能结论。

1. 使用受信任的 HTTPS 打开已打包客户端，记录手机型号、系统、浏览器版本、屏幕刷新率和电源模式。
2. 在「系统诊断」中点击「开始采样」。测启动时先开始采样再启动游戏；测稳定场景时先游玩、热身，再开始采样。
3. 收起面板，在固定存档、视角和场景中游玩 60 秒。保持页面在前台，记录内部渲染倍数；每次对照使用相同条件。
4. 点击「停止采样」和「导出性能 JSON」。分别测试 1×、2×分辨率，至少重复三轮；持续游玩后的结果单独记录，用于观察热降频。

采样默认关闭，每秒记录一次，最多保留最近 300 个样本。停止会清理计时器、帧回调及观察器，报告随后保持不变。后台切换会中断帧时间和核心差分窗口，避免把浏览器冻结的时间当作游戏卡顿。

导出包含核心产物摘要、网页版本、启动偏好白名单、视口、设备能力、核心指标、WASM 容量、ISO 读取延迟直方图和音频计数。不会导出游戏名、文件路径、网址、日志、下载清单或完整配置。镜像和存档继续保留在本地；测试者另行记录场景和设备，便于比较。

## 指标边界

| 指标 | 含义 |
| --- | --- |
| 核心实际 FPS | 核心显示提交计数差除以真实时间；不由页面回调推算 |
| 仿真速度 | PSP 模拟时间增量除以真实时间，100% 代表正常速度 |
| 核心快照 | 由运行仿真的线程发布原子数据，网页通过序号检查一致性；缺少接口、暂停或数据过期时不伪造结果 |
| `frameWallMs` / `lastFrameMs` | 一次 `NativeFrame` 的墙钟时间，包含节拍和渲染等待，不能直接解释为 CPU 成本 |
| 页面帧间隔与长任务 | 网页主线程的响应情况；不覆盖工作线程、GPU 执行时间或所有短任务 |
| 启动阶段 | 从启动点击到 runtime 初始化、游戏启动日志；不等同于首帧。首帧暂记为 `null` |
| WASM 内存容量 | 线性内存可寻址容量，不是有效分配量、设备驻留内存或浏览器进程总内存 |
| 堆调整请求 | 所有原生线程调用分配器扩容接口的完成次数、成功/失败及耗时；一个请求可能在 SDK 内部重试，不等于 `memory.grow` 指令次数。累计耗时也不是整个应用暂停的时长 |
| 容量变化观察 | 录制期间每秒观察到的容量增加；两次采样之间的多次扩容可能合并，不能据此推算准确次数或耗时 |
| 线程资源 | 配置的预建 Worker 数、计算线程数和实际 ThreadManager 线程数分别记录；ThreadManager 不包含模拟器其他线程，也不等于浏览器全部 Worker |
| ISO 读取 | 逻辑请求、排队、物理 Blob 读取分别聚合；请求时间包含排队和缓存处理，三者不可相加。延迟百分位为直方图桶上界 |
| 音频欠载 | 录制区间的新增欠载数；同时保留原始累计计数。零欠载不等同于已经人工听音验收 |

浏览器文件路径下，仿真运行在工作线程，网页主线程处理 GL 队列、输入和音频供给。只采主线程会遗漏主要模拟计算。旧的 [上游性能记录](god-of-war-performance.md) 针对另一条启动路径及历史产物，不代表当前线程结构或当前基线。

## 桌面与 Android 调试采集

用独立浏览器配置启动 Chromium 的本地调试端口，或通过 USB 调试将 Android 浏览器的 DevTools socket 转发到本机。打开播放器并进入指定场景，再运行：

```sh
# 先测量帧率、读取和欠载，不开启 CPU Profiler 或保存画面。
node scripts/profile-browser.mjs --port 9222 --seconds 60 --out .local/baseline --no-profile --no-screenshot

# 再单独采样 CPU。主线程和每个可附加的工作线程分别保存。
node scripts/profile-browser.mjs --port 9222 --seconds 20 --out .local/cpu
```

脚本通过运行时标志识别播放器，即使游戏改变了网页标题也能发现。有多个播放器时必须用 `--target` 指定唯一的完整页面 URL；不会随便选择其他网页。输出 JSON 包含环境、经过白名单筛选的性能配置、核心版本及前后计数，缺失数据记为 `null`。工作线程附加失败会明确列为不可测，不视作空闲。

命令行报告保留 ISO 数字计数和区间差值；读取延迟直方图使用网页中的「导出性能 JSON」获取。出现后台切换、过期快照、暂停或不推进的核心序号时，命令行派生平均 FPS 为 `null`，原始快照和累计差值仍保留用于排查。测量期间不要读档、切换游戏或改变设置。

CPU 采样会扰动运行；各线程采样窗口也可能不同，不能把百分比直接相加成总 CPU 占用。原始 `.cpuprofile` 可能包含源码 URL，默认截图会包含游戏画面，分享前检查内容。脚本不下载游戏，不修改游戏设置。桌面 CPU 限速、移动视口和软件渲染均不能替代手机真机结果。

## 用符号表分析工作线程

发行版 WASM 可以不带函数名，此时浏览器只记录 `wasm-function[编号]`。需要符号时，在原有 Release 链接参数上额外追加 `--emit-symbol-map`，保留源码、SDK、FFmpeg、优化级别和资源配置。以下示例假设现有 `CMAKE_EXE_LINKER_FLAGS` 为空；已有其他链接参数时应保留原值再追加：

```sh
emcmake cmake -S deps/ppsspp-wasm -B deps/ppsspp-wasm/build-wasm-release \
  -DCMAKE_EXE_LINKER_FLAGS=--emit-symbol-map
cmake --build deps/ppsspp-wasm/build-wasm-release -j4
```

该选项生成 `PPSSPPSDL.js.symbols`，内容为函数编号到名称的映射，不包含源码行号。将同一次链接的 WASM、符号表和完整构建产物保存在本地忽略目录中。先比较新旧 WASM 文件的 SHA-256；重新链接不保证与旧产物逐字节相同。不同产物的函数编号不能混用，需要让浏览器加载对应的新核心，再为它建立基线和 CPU 采样。

本地 metadata 至少包含以下两个字段，值填写对应文件实际 SHA-256 的 64 位小写十六进制文本。这里的 `wasmSha256` 是单个 WASM 文件的摘要，不是打包清单里整个核心产物的 `revision`：

```json
{
  "wasmSha256": "<本次 WASM 文件的 SHA-256>",
  "symbolsSha256": "<同次链接符号表的 SHA-256>"
}
```

分别汇总主页面与每条 worker 的原始文件，例如：

```sh
node scripts/summarize-cpu-profile.mjs \
  --profile .local/cpu.worker-1.cpuprofile \
  --wasm .local/symbol-core/PPSSPPSDL.wasm \
  --symbols .local/symbol-core/PPSSPPSDL.js.symbols \
  --metadata .local/symbol-core/metadata.json \
  --out .local/cpu.worker-1.summary.json
```

输出须指定尚不存在的新路径；已有文件会被拒绝，重新汇总时使用新的 `--out` 路径。工具先核对两个文件摘要，再解析编号；摘要不符、符号缺失或同一 profile 含多个 WASM script identity 时拒绝汇总。它不会自动证明采样时浏览器加载的是所提供的 WASM：采集者仍须核对报告里的核心版本、实际打包产物和构建记录。原始 profile 的摘要也会写入汇总，便于复核输入来源。不能拿旧核心的采样配新符号表，即使所有编号都能查到名称。

worker 的 `index` 仅表示附加顺序，`targetId` 是本次调试会话里的不透明身份，都不是线程职责。结合符号化调用栈识别模拟、渲染提交和线程池；不能确认时保留未知。每条捕获记录保留自己的起止时间及实际时长，须与页面计数窗口一起检查。采样窗口因启动、停止或失败而明显延长时，不将它用于原定场景的热点结论。

汇总的 self 表示样本落在该函数，inclusive 包含其子调用；它们都是样本归属的经过时间，包含等待和调度延迟，不是测得的 CPU 执行时间。inclusive 行之间重叠，不能相加；不同线程也不能合成一个 CPU 百分比。`possibleWait` 只是函数名提示，未命中不代表没有等待。限速、条件变量、futex 和睡眠须结合完整调用栈判断，不能因为占比大就删除。该采样也不测 GPU 执行耗时。

工作线程收尾按目标并行停止，同一目标保持停止后再禁用的顺序；重复清理复用同一结果。worker profiler 命令及主线程 profiler 收尾命令默认每条最多等待 5 秒，其他调试命令使用各自的超时，这不是整次采样的总时限。失败的 worker 保留 `unavailable` 和 `failureStage`，禁用失败另记 `cleanupFailed`；这些状态表示未测到或清理未确认，不能当作空闲。成功返回的部分 profile 仍需逐一检查时间窗口。

## 活跃工作线程的浏览器级追踪

如果普通采样在活跃 WASM 线程的 `Profiler.enable` 阶段超时，可以显式使用 `--trace-cpu`。它调用浏览器级 V8 Tracing，不依赖逐 Worker 启用 Profiler；普通模式不会自动切换到这条路径。浏览器内部导致超时的确切原因尚未证实，不能仅凭同步 WASM 循环断定是事件循环阻塞。

Tracing 覆盖整个浏览器实例。必须使用独立配置启动的专用调试浏览器，只打开被测播放器；采样中不要新增标签页或其他目标。工具在开始时拒绝额外页面、共享 Worker、Service Worker 和后台目标，但这个检查不能代替专用浏览器隔离。它只启用 CPU profile 分类，不开启截图、网络或系统追踪分类；原始栈仍可能含源码 URL，留在本地忽略目录。

```sh
node scripts/profile-browser.mjs --port 9222 --seconds 20 \
  --out .local/scene-trace --trace-cpu --no-screenshot

node scripts/extract-trace-profiles.mjs \
  --trace .local/scene-trace.trace.json \
  --metadata .local/scene-trace.trace-meta.json \
  --out-dir .local/scene-trace-profiles
```

随后对 `scene-trace-profiles/` 中每份 `.cpuprofile` 使用前节的符号汇总命令。`manifest.json` 保留进程、profile 标识、原始采样线程与文件摘要；线程职责仍以调用栈判断。Trace 分片可能由另一条线程写出，提取器按进程及 profile 标识归组，不能按分片的 `tid` 合并。

采集通过 JSON 流分块写入，输出上限 128 MiB，逐命令、结束通知和读流均有截止时间。Trace 与元数据采用排他创建；提取也只接受尚不存在的新目录。只有捕获完成、数据丢失标记明确为 `false`、摘要匹配且结构有效时才能提取；失败或未知状态不生成有效热点结论。`cleanupFailed` 表示流或文件清理未获确认，须保留这个状态。

当前实测 trace 没有记录各线程的停止时刻。提取器将 `endTimeSource` 标为 `last-sample`，边界只到 `startTime + sum(timeDeltas)`，汇总的 `unassignedTailUs` 为 `null`。这不表示尾部为零，也不表示已经知道完整采样时长。若格式提供明确的结束时刻，则保留 `recorded` 边界并校验样本没有越界。

Tracing 的采样间隔由浏览器实现控制，报告因此记为 `null`，不能当作普通 Profiler 的 1,000 微秒。当前 [V8 实现](https://raw.githubusercontent.com/v8/v8/main/src/profiler/tracing-cpu-profiler.cc) 使用更高频的内部采样，但这不是所有浏览器版本的固定承诺。调用依据是 [CDP Tracing 协议](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/)。热点比例包含等待、调度及采样开销，帧率与音频基线仍必须另用 `--no-profile` 采集。

## 内存和线程的独立对照

默认仍为 512 MiB 初始容量、4 GiB 上限、2 个计算线程；ThreadManager 另建 4 个 I/O 线程。默认预建 Worker 数沿用 `max(4, hardwareConcurrency)`。计算线程数与预建池是两个参数，不能用浏览器 Worker 总数推断 CPU 并行度。

激活 SDK 并准备好已有的 FFmpeg 构建目录后，可以只改变一项重新配置、编译：

```sh
# 保留其他编译选项，分别测试 268435456 / 402653184 / 536870912 字节。
emcmake cmake -S deps/ppsspp-wasm -B deps/ppsspp-wasm/build-wasm-release \
  -DWASM_INITIAL_MEMORY=268435456 -DWASM_COMPUTE_THREADS=2 -DWASM_PTHREAD_POOL_SIZE=auto
cmake --build deps/ppsspp-wasm/build-wasm-release -j4

# 线程池实验另开一组，初始内存保持 512 MiB。
emcmake cmake -S deps/ppsspp-wasm -B deps/ppsspp-wasm/build-wasm-release \
  -DWASM_INITIAL_MEMORY=536870912 -DWASM_COMPUTE_THREADS=2 -DWASM_PTHREAD_POOL_SIZE=12
cmake --build deps/ppsspp-wasm/build-wasm-release -j4
```

也可以把同名参数传给 `make wasm-release`。内存必须按 64 KiB 对齐且不超过上限。计算线程允许 1–32 个，改变它时必须指定固定预建池；固定池要求至少 `compute + max(4, compute) + 6` 个 Worker，最多 128 个。预留量覆盖常见启动线程，额外子系统仍可能需要更多。固定池用严格模式：用尽即报告线程创建失败，避免同步等待异步创建的 Worker。它是实验参数，不能凭一次启动就推断所有游戏功能都适配了较小线程池。

构建前后分别运行 `python3 scripts/fingerprint-wasm-source.py`，确认摘要相同，再将该值传给 `scripts/package-player.py --source-fingerprint <SHA-256>`。使用独立编译缓存时，必须加 `--source-root <实际编译的核心源码目录>`，让摘要来自真实编译树。该工具从 Git 清单选择文件，不包含被忽略的游戏和构建输出。打包只提取资源数字，不复制 CMake 中的路径。源码摘要不是产物签名，也不自动验证工具链、FFmpeg 或其他编译选项；这些条件仍要固定。

每次使用独立浏览器配置、相同存档、同一启动操作序列和场景。每个变体至少录两轮 60 秒，交错次序，保持网页与核心其他设置、浏览器版本、电源状态及缓存准备方式一致。游戏、存档、截图和原始报告放在忽略目录，不放进站点目录。只有浏览器文件选择器读取本地游戏。

将网页「导出性能 JSON」保存后，建立本地清单，例如：

```json
{
  "schemaVersion": 1,
  "dimension": "initialMemoryBytes",
  "environment": { "id": "desktop-session", "kind": "desktop" },
  "scene": { "id": "opening-video", "alignment": "manual" },
  "runs": [
    { "id": "baseline-a", "pair": "a", "report": "baseline-a.json", "value": 536870912 },
    { "id": "candidate-a", "pair": "a", "report": "candidate-a.json", "value": 268435456 },
    { "id": "candidate-b", "pair": "b", "report": "candidate-b.json", "value": 268435456 },
    { "id": "baseline-b", "pair": "b", "report": "baseline-b.json", "value": 536870912 }
  ]
}
```

运行 `node scripts/compare-browser-performance.mjs --manifest .local/matrix.json --out .local/comparison.json`。线程池维度为 `pthreadPoolSize`（0 表示自动），计算线程维度为 `computeThreads`。自动场景标记可使用 `alignment: "emulated-time"` 并给出 `startEmulatedUs`；它只核对模拟时间，不验证画面或游戏状态相同。

比较器独立从原始计数重算时长加权 FPS 和仿真速度，要求有效时长至少 60 秒、覆盖率至少 95%。缺少源码摘要、采样字段、配置不一致、后台切换、计数回退或时长不足时返回 `invalid` / `incomparable`，退出码 2，不给出变体性能结论。`comparable` 仅表示这些检查通过，不代表统计显著提速。新报告为 schema 2；旧报告仍可读取查看，但缺少复核字段，不能混入本组比较。

## 本轮本地对照

2026-10-24 使用 Windows、Edge 157、Intel D3D11 硬件渲染、844×390 视口、DPR 1、1×内部渲染，运行本地镜像的有声 30 FPS 视频片段。这里只建立桌面对照，没有连接 Android 真机，也未测 iOS、战斗场景、长期热降频或整机功耗。

音频泵采用同页交替的 `2 / 8 / 8 / 2 ms` 设置，各稳定 1 秒后测 15 秒；不同时启用 CPU Profiler。每段音频回调 703–704 次，有声探测 44 次。

| 请求检查间隔 | 实际每秒检查次数 | 仿真速度 | 实际 FPS | 新增音频欠载 |
| --- | --- | --- | --- | --- |
| 2 ms，第一段 | 249.58 | 99.29% | 29.76 | 0 |
| 8 ms，第一段 | 124.99 | 99.99% | 29.97 | 0 |
| 8 ms，第二段 | 124.95 | 99.28% | 29.76 | 0 |

## 游戏重启时的内存释放

检查 `NO_MMAP` 路径时发现，`Find4GBBase()` 为 PSP 地址空间分配的 160 MiB 缓冲区没有在 `ReleaseSpace()` 中释放。游戏关闭时虽然清空了视图与全局基址，底层分配仍然存活；同页重启游戏会再次分配。现在由 `MemArena` 保存唯一的所有权，视图继续借用内存，在原有关闭流程中统一释放并清空指针，重复查询和重复释放均安全。

## IR 块计数诊断

`-DWASM_IR_BLOCK_PROFILE=ON` 仅用于本地诊断，默认关闭。它在 IR 块入口增加一次计数，保存编译时的静态 IR，并在帧边界处理开始、停止请求。每轮运行循环使用已有递归锁串行化缓存事件与统计发布；逐块不读时钟、不加锁。正常 OFF 构建不编译诊断模块，也不包含新增入口调用与导出。

注册表最多保存 65,536 块和 1,048,576 条静态 IR。导出包含所有触达块的加权静态 opcode 直方图，以及按入口次数排序的前 32 块，每块最多 128 条 IR。截断会显式标记。加权值为「块入口次数 × 块内静态出现次数」，条件退出后的指令可能没有执行，因此它不是精确指令执行量，更不是 CPU 耗时。完整缓存清除、停止仿真、模拟时间回退、注册预算耗尽、未知块或计数溢出都会使当前轮次失效。

开始／停止请求仅通过原子队列进入核心；报告也使用原子字段及相同的偶数序列号校验，避免跨线程读到一半的报告。请求必须等待帧边界确认，并核对本轮 capture ID。不会直接从浏览器读取仍在扩容的 IR 缓存。冻结、排序和导出有额外开销，诊断版的 FPS 不能用于证明优化收益。

本地使用方式如下，先启动独立调试浏览器并在播放器中进入目标场景：

```sh
# 使用已经验证可运行的 Emscripten 构建目录，保留 FFmpeg、内存和线程参数。
# USE_NO_MMAP 必须开启，以选择浏览器所需的内存分配路径。
emcmake cmake -S deps/ppsspp-wasm -B <diagnostic-build> -DWASM_IR_BLOCK_PROFILE=ON
cmake --build <diagnostic-build>
python3 scripts/package-player.py --build-dir <diagnostic-build> --allow-diagnostics
node scripts/profile-ir-blocks.mjs --port <local-debug-port> --target <exact-player-url> --seconds 20 --out .local/ir-report.json
```

打包器默认拒绝带该开关或导出标识的核心；`--expected-revision` 不能绕过，只有显式 `--allow-diagnostics` 才放行。构建元数据记录 `diagnostics.irBlockProfile`。采样后应重新打包 OFF 核心，性能 A/B 比较也必须使用 OFF 构建。原始报告包含游戏代码片段、地址与常量，和游戏、存档一样只放忽略目录，不提交或公开。分析 opcode 名称时应使用对应构建的 `IRInst.h`，不能套用其他核心版本的枚举。

### 两段固定场景的计数结果（2026-10-25）

| 移动 | 44,039,786 | 351,618,095 | 23.855% | 0.00949% |

前 32 块覆盖的加权静态 IR 分别为 28.438% 和 26.224%，不代表全部代码。两段均在同一个高频块内看到 11 处相邻的 `MfLo → Mult`，目标寄存器不与后续乘法的两个源重叠；按块入口加权分别为 4,439,160 和 4,227,960 次。该块没有中间条件退出，主要由整数乘加、夹取和 16 位写入构成，适合先实验减少解释分派。通用解释回退的静态占比较低，当前证据不足以优先投入 VFPU 回退改写；这不等于证明其耗时也同样低。

### 整数乘法融合试验及撤回

实验候选将相邻、寄存器不重叠的 `MfLo → Mult` 合成一个解释器专用 opcode，保留旧 LO 到目标寄存器，再计算并写入完整 HI/LO；仅在解释器的最终优化 pass 生成。实际生产 pass 与解释器分别编译为原生程序和 WASM，各通过 20,730 组状态差分，覆盖符号边界、随机状态、HI/LO、链式乘法、重叠拒绝以及优化边界。语义测试通过并不能证明性能收益。

随后关闭诊断，以相同迷宫存档、浏览器、1×渲染和资源配置运行 A／B／B／A。每轮使用新的浏览器 context、禁用 Service Worker，保持游戏音频运算，读档后静止；按 5 秒模拟时间预热，再测约 60 秒模拟时间的快进吞吐。快进改变呈现和音频缓冲策略，下表不是正常播放 FPS、CPU 利用率或音质比较。

| 次序 | 核心 | 墙钟秒 | 模拟秒／墙钟秒 |
| --- | --- | --- | --- |
| A1 | 原版 | 29.225 | 2.055100 |
| B1 | 融合候选 | 29.384 | 2.042813 |
| B2 | 融合候选 | 29.258 | 2.053914 |

按总模拟时间除以总墙钟时间计算，原版为 2.053739，候选为 2.048352，相对差异约 −0.2623%。B1 较低，B2 落在 A 两轮之间，没有重复稳定的收益，也不足以证明性能回退。实际模拟起点相差最多 166.833 毫秒，终点超出目标最多 93.353 毫秒，各轮物理读量也不同；每版只有两轮。约 2 倍只是这组快进结果，未证明任何 CPU 上限。

### 固定场景的初始内存对照（2026-10-26）

本轮沿用上述正常核心，分别构建 256、384 MiB 变体，与 512 MiB 参考构建比较。构建前恢复了缓存中尚未撤回的融合候选文件，再核对构建时工作区与编译缓存的完整源码；摘要均为 `ca7d769beebbb77ae325872cb67c9f198eb74df0bfe0658448afbe11c5bc99ab`。138 项 CMake 布尔与字符串参数中，仅 `WASM_INITIAL_MEMORY` 不同，诊断功能关闭，线程池、最大容量和编译器保持一致。WASM 摘要分别为 `f51c2b0d4122d8ccde2cb30a714b72654ac6934ae391e0344f127f2eecd82ebe`（256 MiB）、`f3c786d52de07c317ae15c7f7654287fd679a2fbdc7b2e77024e36878ab3f1c7`（384 MiB），512 MiB 沿用上述参考产物。

每个场景使用全新无头 Edge `157.0.4341.16` 实例、1×渲染、关闭 Service Worker，只导入目标存档并读档一次，关闭读档撤销缓存。启动运行 5 秒模拟时间后读档，分别记录读档前、首次读档后、采样前后的原生容量与累计扩容计数；移动从模拟时间 1680 秒、战斗从 1801 秒附近开始录制。沿用方向短按与战斗输入序列，截图在计时窗口外完成。先按 512、256、384 MiB 运行，再反向运行；每段请求 60 秒，不启用 CPU Profiler。

实际 WASM GET 响应先由测试脚本计算摘要，再把同一份字节交给浏览器；此方式会禁用 HTTP 缓存，对所有配置一致。最初直接读取调试接口响应体时遇到缓存驱逐，该次在录制前失败并保留记录，不计入样本。浏览器逐秒原始报告另由 `compare-browser-performance.mjs` 检查至少 60 秒有效区间、95% 有效覆盖、可见性、设置与起点容差，并按有效时长重算帧率；原生 CDP 计数窗口也独立核对起点在目标的 250 毫秒以内。

### 即时存档的压缩输入分块（2026-10-26）

先同步上述依赖锁文件更新，并对工作区、构建缓存及编译后的 24,917 项源码核验。新基线源码摘要为 `4661f0e959656bcc037a1ed900249e53cb0bf1bc3c26e802ad7cf7ad2cab7062`，WASM 字节仍与原参考构建一致。候选仅修改 `Common/Serialize/Serializer.cpp` 及其 bundled ZSTD 编译标记，源码摘要为 `1e6293a15f598ec43558ffcf3285351982851d1ce025e481ffe441e697dc3936`，WASM SHA-256 为 `b28c7055b5cbfa54d9ca09f8e42261055ac25850565eed788e0ed3bcb274e01b`。构建前后全部 138 项布尔与字符串参数一致，初始容量 512 MiB、最大 4 GiB，诊断关闭。

原路径同时分配完整压缩输入和解压输出。候选仅在网页构建使用随附 ZSTD 库时启用稳定输出流式接口，以最多 1 MiB 的输入块解压，完整输出仍须保留给状态恢复。系统库、缺少参数的头文件、版本或参数不匹配时保留原路径。复核发现 one-shot 能接受最大窗口指数带非零尾数的合法帧，流式接口却会拒绝；候选仅对确切的窗口过大错误释放全部流式存储、重新定位并交给原解码器校验，定位失败直接拒绝。普通损坏、短读、长度错误或无进展不重试；该特殊兼容回退仍可能分配完整输入。

`test-state-zstd-input.py` 在 Linux 直接编译实际加载实现、模板和压缩库，仅文件 I/O 与日志使用测试替身。网页、原生、模拟缺少参数的头文件、无 bundled 标记网页及系统 ZSTD 五种路径各通过 176 个差分用例，共 880 个，覆盖跨输入块回引用、已知／未知输出长度、串联／跳过／空帧、校验和／截断／尾垃圾、短读、旧版头、窗口兼容回退及定位失败。合成样本的已知数组峰值由 10,485,931 降至 6,291,473 字节，流式上下文观测为 227,048 字节；数组和上下文分别记录，未测量 one-shot 内部上下文，也不是全堆或进程内存。此前遗漏最大窗口尾数的测试及失败复现继续保留。
